# PORT SABLE — narrative state, mission branches and save contract

## Purpose

PORT SABLE is built around remembered choices. A prologue decision must affect later scenes or mission presentation; otherwise the choice is cosmetic. This document defines the small, explicit persistence contract used by the first three lead introductions and future campaign branches.

## Persistent prologue flags

`NarrativeStateLedger` stores integer values under stable string IDs. The opening dialogue graphs currently write:

| Flag | Values | Meaning |
|---|---|---|
| `mara_race_choice` | 1 / 2 | Mara accepts Nico's driving challenge / declines and stays focused on the delivery |
| `rafi_event_choice` | 1 / 2 | Rafi honours the first promise / protects the headline event with a revised slot |
| `rafi_staff_responsibility` | 1 / 2 | Rafi personally tells the performers / makes Mina announce the change |
| `elias_settlement_choice` | 1 / 2 | Elias witnesses the settlement / refuses to sign for Silas |

Do not recycle these IDs for unrelated choices. New flags need a unique ID, a documented value map and at least one downstream consumer.

The prologue dialogue generator writes the values on the choice itself. `DialogueController` publishes any mission signal, applies a relationship delta and writes the persistent flag when that choice is selected. If a scene has not instantiated `NarrativeStateLedger`, the controller logs an error rather than silently pretending the choice was saved.

## Branch conditions

A `MissionBranchCondition` must use exactly one source:
- `relationshipKey`: reads a character relationship value from `NPCRelationshipLedger`;
- `storyFlagId`: reads an explicitly stored integer from `NarrativeStateLedger`.

A story flag that has never been set does **not** match a numeric range containing zero. This prevents an unplayed prologue from silently being interpreted as the player choosing option 0. Conditions in a branch are ANDed. Branches are evaluated in array order; the first matching branch with a valid forward target wins. If no branch matches, the director uses its explicit fallback mission ID or the next campaign asset in sequence.

Branch IDs must refer to mission assets in the configured `MissionDirector.campaign` array. The director refuses backward or missing targets and logs a warning. Ending mission assets should set `endsCampaign` so the director stops instead of accidentally advancing into a different ending.

## Save schema v3

`SaveSnapshotStore` writes schema v3 under `project_tideline.save.v3`. It stores:
- active playable lead ID;
- the last world-space position and yaw for each of the three lead actors;
- mission/objective progress;
- world time;
- relationship ledger data;
- narrative flag ledger data;
- the existing fictional public-attention value.

Read compatibility is maintained in this order: v3, v2, v1. V1/V2 saves only held the selected player position and no full multi-lead state; they are restored using that legacy position and the saved active lead when available. A fresh v3 save captures all three lead transforms.

### Vehicle-save guard

The current snapshot does not serialize a vehicle's rigidbody, wheel state, route state or occupant relationship. Therefore `SessionSaveCoordinator` refuses a save while the active lead occupies a vehicle or is transitioning into it. This deliberately preserves the previous valid save instead of writing the actor's seat-parented position as a false on-foot checkpoint.

Vehicle-state serialization is a separate future task. Do not remove this guard until vehicle transform, velocity, damage/state, occupied seat and traffic-driver ownership are all represented and tested.

## Required scene wiring

The persistent bootstrap scene needs exactly one:
- `NarrativeStateLedger`;
- `NPCRelationshipLedger`;
- `MissionSignalBus` (static class; no GameObject required);
- `MissionDirector`;
- `SessionSaveCoordinator`;
- `PlayableLeadSwitcher`.

The four dialogue graphs across the three prologues are generated by **Project Tideline → 9 — Generate PORT SABLE Prologue Dialogue** (Mara has separate opening/work-order and post-delivery Nico graphs). Their structure and required flag values are checked by **Project Tideline → 10 — Audit PORT SABLE Prologue Dialogue**.

The dialogue audit validates graph data only. It does not prove that each graph is assigned to an NPC, that the scene UI is wired, or that a player can complete the prologue.

## Verification matrix

| Check | Evidence required |
|---|---|
| Graph IDs and node links | Unity Editor dialogue audit report |
| All prologue flags and values | Unity Editor dialogue audit report |
| Flag values after choices | Play Mode capture/log plus saved PlayerPrefs snapshot |
| Mission branch selection | Play Mode branch tests for every value and unset flag |
| V1/V2 migration | Import old save fixtures and verify active lead/position |
| V3 multi-lead restore | Save each lead in a different location, restart and compare all transforms |
| Vehicle save guard | Attempt save while seated and during handoff; confirm previous save remains unchanged |
| Android persistence | Pause/resume and cold-restart tests on the exact Vivo T2x RAM SKU |

No verification is considered passed until the Unity Editor or device has generated the evidence. Static file presence alone is not a pass.
